# Session Prompt: Blades CSS HTML Export Migration

## What this is

You're in a git worktree for `feature/blades-css-html-export`, branched off latest `origin/master`. This is a separate worktree from the main heimdall2 checkout (which is running the attestation engine work on a different branch in a different session). They won't collide.

## Your task

Migrate Heimdall's HTML export from Tailwind CSS + TW Elements (825KB of CSS+JS per exported file) to Blades CSS (~12KB, zero JS). The user wants this done thoroughly — over-plan, deep-review, then execute with confidence.

## Phase 1: Deep Review (do this FIRST)

Use a multi-agent workflow to review the plan from every angle before writing any code:

1. **Template audit** — Read `libs/hdf-converters/data/reverse-html-mapper/template.html` (568 lines) end-to-end. Catalog every Tailwind class, every TW Elements `data-te-*` attribute, every Mustache variable used. Produce a complete feature inventory.

2. **Blades CSS capability verification** — For EVERY feature found in the template audit, verify that Blades CSS can replace it. Fetch actual Blades docs (https://blades.ninja/, npm `@anyblades/pico`). Flag any gaps.

3. **Mapper code audit** — Read `libs/hdf-converters/src/converters-from-hdf/html/reverse-html-mapper.ts` (524 lines) completely. Document every place that touches `tailwindStyles`, `tailwindElements`, `js`, or template rendering. Identify all changes needed.

4. **Consumer analysis** — Find every file in the entire repo that imports from or references the HTML export. Check ExportHTMLModal.vue, PrintButton.vue, CLI export commands, and anything else. Map the full blast radius.

5. **Test strategy** — Read the existing test file (3 snapshot tests). The snapshots will ALL break after the template rewrite. Plan: how to regenerate, what new tests to add, how to verify correctness beyond snapshots.

6. **Dependency audit** — Confirm exactly what gets removed (tailwindcss, @tailwindcss/cli, tw-elements) and what gets added (@anyblades/pico or vendored CSS). Check for any transitive dependency impacts.

Synthesize all findings into a revised, airtight execution plan before touching any production code.

## Phase 2: Execute with TDD

After the review is complete and the plan is solid, implement card-by-card using TDD:
- Failing test first, then implementation, then green
- Build after each card
- Regenerate sample HTML snapshots when template changes
